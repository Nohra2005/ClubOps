# Design log

Every design choice, in the order it was made, with the alternatives considered and the reason. It feeds the final report's design-choices section. Bigger choices also get an ADR in `adr/`.

Status: **decided** · **proposed** (awaiting the owner's confirmation) · **superseded**.

| # | Date | Decision | Alternatives considered | Why | Status |
|---|---|---|---|---|---|
| D-01 | 2026-10-12 | One OpenAI-compatible model client over `httpx`, provider set by configuration | A provider SDK; a framework (LangChain etc.) | Minimal dependencies; switch provider without code changes | decided |
| D-02 | 2026-10-12 | Model calls run in `replay` mode by default; `record` and `live` on request | Always live | Free, reproducible results without API keys (brief: reproducibility) | decided |
| D-03 | 2026-10-12 | Free model tier for synthetic data; a cheap paid provider that does not train on inputs for real club data | One provider for everything | Cost limit set by the owner; real chats must not be used for training | decided |
| D-04 | 2026-10-12 | Recordings of real-data model calls are never committed | Commit all recordings | They contain club data | decided |
| D-05 | 2026-10-12 | AUB-wide rules stored once for all clubs; the system is multi-club, tested on the Running Club | One store per club | Rules must not be duplicated; avoid a running-only design | decided |
| D-06 | 2026-10-12 | All cabinet members use the system; the adviser is read-only | President only | Matches how the club works | decided |
| D-07 | 2026-10-15 | The agent never creates, redraws or retraces a logo; it uses official files and asks the owner when a file is too small | Recreate logos from images | A redrawn logo is wrong and misrepresents the brand (found during the Oct 18 triathlon work) | decided |
| D-08 | 2026-10-21 | Tatiana owns `capture` and the evaluation datasets | Split capture and evaluation | Capture labels (D1) must exist before capture is built, so one owner is simpler | decided |
| D-09 | 2026-10-21 | Before any text reaches the model, phone numbers, AUB IDs and e-mail addresses are replaced with placeholders; names are kept. Extracted items do not record who said what | Redact nothing; also redact names | Brief requires "secret and PII protection" and memory privacy considerations; names of offices and contacts are part of the know-how (who decides what) | decided |
| D-10 | 2026-10-21 | Separate contacts store (name, role, organization, channel, phone/e-mail), cabinet-only, never sent to the model or quoted; know-how items point to it with `contact_ref` | Contacts inside know-how items; no contact details | The cabinet needs contact details; the model does not | decided |
| D-11 | 2026-10-21 | Rule items carry a source authority: `official_document` > `office_email` > `stated_by_president`. A weaker source that conflicts with a stronger one becomes a contradiction for a person to resolve | Treat all sources equally | Oct 15: a rule stated verbally ("Red Bull allowed") was overruled by an office (Athletics). Becomes a regression test | decided |
| D-12 | 2026-10-21 | Asset registry for files (logos, templates, signed agreements): owner, source, official yes/no, resolution or vector, allowed uses; know-how items can point to assets | Keep files outside the system | The agent guessed logos when no official file was recorded (see D-07) | decided |
| D-13 | 2026-10-21 | Hybrid memory: verified know-how items are the source of truth and are retrieved first; redacted chat excerpts are a fallback, always shown as "unverified". Plain RAG over raw chats is kept as an evaluation baseline | RAG over raw chats only; verified items only | Know-how changes and gets overruled; plain RAG returns old and new versions alike. Comparing the two answers the brief's "compare design choices" | decided |
| D-14 | 2026-10-21 | Raw exports are deleted after capture, but a redacted excerpt store is kept outside the repo; it is the evaluation data, the RAG baseline's corpus and the hybrid fallback | Delete everything after capture | Capture cannot be evaluated or audited without the source | decided |
| D-15 | 2026-10-21 | Staff e-mails are captured with names: AUB staff are public office holders stating rules. Presidents' chat: only messages from OSA staff (Tala Charif, Lynn Berbary) and important official updates are captured; other presidents' names are removed | Use everything; exclude both | Brief requires authorized data; office holders speak for their office, while other presidents' messages are their clubs' business | decided |
| D-16 | 2026-10-21 | Tatiana labels all of D1 (150+ items) before capture is built and the file hash is frozen; one cabinet member independently labels 30 excerpts so agreement between the two labellers is reported | One labeller only; a model as second labeller | Shows the answer key is not one person's opinion; a model would be the system grading itself | decided |
| D-17 | 2026-10-21 | Chats are cut into episodes at silences (6 hours, and always at a gap over a day) | Fixed-size chunks; model-based topic splitting | Club tasks are discussed in bursts; no model cost; episodes are natural units for D1 and the excerpt store | decided |
| D-18 | 2026-10-21 | Voice notes, images and documents omitted from exports are counted and reported as a limitation; episodes that are mostly omitted media are marked low-evidence | Transcribe voice notes | Lebanese-dialect transcription is unreliable and out of scope for now | decided |
| D-19 | 2026-10-21 | Capture keeps only reusable know-how (procedures, lessons, contacts, gotchas, decisions with reasons, rules, yearly rhythms) and ignores one-off logistics, social chat and anything true only that day. D1 uses the same definition | Capture everything and filter later | Most chat lines are not know-how; agent and answer key judged by one definition | decided |
| D-20 | 2026-10-21 | Before proposing an item, capture searches existing items; a match becomes a merge proposal that adds support instead of a duplicate | Allow duplicates; deduplicate offline | Recurring facts (weekly runs) would otherwise appear dozens of times | decided |
| D-21 | 2026-10-21 | An event history store (name, date, type, participants, sponsors, outcome), extracted by capture and verified like items; know-how support points to it | Keep events only as tags | Lessons cite events; answers like "how many came last year" need it | decided |
| D-22 | 2026-10-21 | Items are written in plain English; quotes stay in the original language (English, Arabic, Arabizi). D1 includes Arabizi excerpts | Keep items in the source language | Consistent search and handover packs; quotes keep items checkable; Arabizi handling is measured | decided |
| D-23 | 2026-10-21 | Two separate stores: General (AUB-wide, shared by all clubs, stored once) and Club know-how (one per club) | One store with a scope tag | Different sources, update cycles, writers and readers; separation makes "stored once" and "no leaks between clubs" hold by design | decided |
| D-24 | 2026-10-21 | General holds AUB rules, AUB offices and who decides what (with contacts), AUB-wide procedures, and forms/templates and asset rules | Rules only | All of these are true for every club; a contact learned by one club helps the others | decided |
| D-25 | 2026-10-21 | Adding or changing a General item needs an official source (document, office e-mail, or a message from OSA staff) and confirmation by a second president from another club, chosen at random | Any president; official source only | One president cannot change what every club sees; random choice prevents two presidents colluding | decided |
| D-26 | 2026-10-21 | When club know-how is true for every club, capture also proposes it to General (subject to D-25); the club keeps its own lesson pointing to the General item | Keep it club-only | Example: Athletics blocking energy-drink sponsors (Oct 15) applies to all clubs | decided |
| D-27 | 2026-10-21 | Presidents teach the agent directly: a sentence about something new becomes a proposal (club know-how verified by the club's cabinet; General items through D-25) | Learn only from imported chats | Continuous learning from use is the main point of ClubOps; presidents learn rules first-hand | decided |
| D-28 | 2026-10-21 | Student Affairs e-mails reach ClubOps by manual forwarding from a president to a ClubOps inbox; they go through redaction, injection flags and verification like chats. Automatic forwarding and a direct AUB Outlook connection stay possible later on the same intake path | Direct Microsoft Graph connection (needs AUB IT approval); automatic forwarding rules (may be blocked by AUB) | No dependency on IT approval; the president chooses what is relevant; worth testing as the simplest path | decided |
| D-29 | 2026-10-21 | AUB's planned Moodle for clubs is noted as a future source, not built. Sources plug into one intake step, so a new source is an adapter, not a redesign | Build for Moodle now | Launch date unknown | decided |
| D-30 | 2026-10-21 | Rule refresh: the agent checks the official OSA pages (aub.edu.lb/SAO/activities/Pages/ and the documents they link) once a month. When a page or document changed (content hash differs), it re-extracts the rules and proposes updates through D-25; items citing the old version are flagged "re-check". Once the yearly update has arrived, monthly checks pause until the next September | Re-check only when someone uploads a new handbook; check continuously | OSA publishes its yearly updates around the end of October; the official website is the up-to-date source | decided |
| D-31 | 2026-10-21 | Documents on aub.policytech.eu (Athletics facilities guidelines, Student Code of Conduct, Online Communication Policy) cannot be fetched by a script. From September, the president gets one monthly reminder to check and upload them; reminders stop once the updated versions are uploaded and restart the next September. A failed fetch of any source raises a warning, never a silent "no change" | Headless browser fetching; skip these documents; remind every month all year | Reliable without fragile scraping; reminders only during the yearly update season so presidents are not disturbed | decided |
| D-32 | 2026-10-21 | If the randomly chosen president does not respond within 72 hours, another is chosen at random. With fewer than two clubs, General items stay "pending confirmation" and are treated as unconfirmed; ASME is seeded as a second club for the demo | Wait indefinitely; skip confirmation when only one club exists | Keeps D-25 working without blocking; never treats an unconfirmed rule as fact | decided |
| D-33 | 2026-10-21 | Proposals are reviewed in batches, one chat episode per screen, rules first; merges into existing items are pre-ticked. Review time per item is recorded as a cost metric | Review proposals one by one | Hundreds of proposals from the first import; review effort is a real cost worth reporting | decided |
| D-34 | 2026-10-21 | Inputs: chat re-exports (only messages since the last import), forwarded e-mails (D-28), president notes (D-27), document uploads, and a post-event debrief form that becomes lessons (aligned with OSA's Post-Event Impact Report) | Only the initial chat import | Continuous learning; the debrief is the cleanest source of lessons | decided |
| D-35 | 2026-10-21 | Storage: SQLite with full-text search (FTS5); one database per club and one shared General database; contacts and assets as separate tables; the excerpt store is a separate database outside the repo. Embeddings only if evaluation shows a gain (ADR 0004) | A vector database from the start | Hundreds of items, not millions; fewer moving parts; retrieval choice backed by evidence | decided |
