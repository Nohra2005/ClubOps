# Deploy ClubOps (C-18 / C-14)

**Status, 26 October 2026:** deployment files are prepared; no service, paid resource,
OAuth client or production URL has been created. The local API and production router
are tested with synthetic data. A container build still needs a running Docker engine.

## Hosting decision needed

The existing task asks for a free Render service with persistent SQLite storage.
[Render Free does not support persistent disks](https://render.com/docs/free).
Its local files are ephemeral. The prepared `render.yaml` therefore describes one
**paid** `0.5c-512mb` service and a 1 GB disk, with automatic deploys disabled.
Review the current price in Render and obtain the account owner's agreement before
creating it. A free deployment requires a separately approved storage design change.

The image serves React and `/api` on one origin using Caddy, with one API worker.
Render handles public HTTPS; Caddy listens internally on `$PORT`. Secure HttpOnly
cookies stay on the same origin. The disk stores the shared rulebook, club databases,
run records and private telemetry. Keep this service to one instance; background runs
are in-process, so let active planning finish before a manual deploy/restart.

## Google setup

1. In Google Cloud, create an OAuth **Web application** client for ClubOps and configure
   the consent screen. If it is in testing mode, add the intended cabinet test users.
2. Add the exact deployed origin to **Authorized JavaScript origins**, plus local
   `http://localhost:5173` or `http://127.0.0.1:5173` when needed for development.
3. Put the same public `.apps.googleusercontent.com` ID in both
   `CLUBOPS_GOOGLE_CLIENT_ID` and `VITE_GOOGLE_CLIENT_ID`. The latter is compiled into
   the frontend, so changing the ID requires a rebuild. Startup rejects a mismatch.
4. Add each member's chosen Google email to the cabinet list. University Microsoft
   accounts are not Google identities; do not require an AUB domain (D-68).

This uses the GIS JavaScript callback and ID-token exchange; it does not need a
frontend OAuth client secret or an invented redirect endpoint. See the official
[Google setup guide](https://developers.google.com/identity/gsi/web/guides/get-google-api-clientid).

## Provision when the account and budget are settled

1. Connect this repo to a Render Blueprint and review the proposed service/disk.
   Keep `autoDeployTrigger: off` until verification is complete.
2. Fill the prompted environment values. Provider URL, model, API key and **actual
   input/output token prices** come from the selected provider; zero is not a placeholder
   for unknown prices. The server session secret is generated by Render.
3. Deploy. The startup command loads the versioned, sourced rulebook idempotently.
   No real people are baked into the image. In the service shell, bootstrap the president:

   ```sh
   python scripts/add_member.py <club-id> "<president name>" <google-email> president
   ```

   These are local placeholders, not values to commit. The president can add the rest
   of the cabinet in Settings. Keep `CLUBOPS_DEV_LOGIN=0` and `CLUBOPS_COOKIE_SECURE=1`.

4. Open `/events` directly, sign in with Google, plan an event, inspect the result,
   and approve only after review. Check the calendar, logout, and cross-club access.
   Restart the service and verify that approved records remain. Record the URL and
   outcome before marking C-18/C-14 complete.
5. Back up the persistent databases with SQLite's backup API and keep exports private.
   A disk is persistence, not a tested recovery plan. Never commit backups or recordings.

See [Render Docker builds](https://render.com/docs/docker) for public build arguments
and [disk behavior](https://render.com/docs/disks). Only the public Google ID is consumed
as a Docker build argument; provider keys stay in runtime configuration.

## Local packaging checks

With Docker running, from the repo root:

```sh
docker build --build-arg VITE_GOOGLE_CLIENT_ID=<public-client-id> -t clubops .
# Supply real configuration in an ignored file and mount a named data volume.
docker run --rm -p 10000:10000 --env-file .env -v clubops-data:/var/data clubops
```

Use `http://localhost:10000` only for a packaging check. Google session cookies require
HTTPS in this production entrypoint; local browser authentication tests use the
isolated dev fixture instead. Tests and dev-login fixtures are excluded from the image.

Without Docker, install Caddy and build/test the same static routing locally:

```sh
cd web
# Set VITE_API_MODE=http before the build (and the public Google ID for real sign-in).
npm run build
npm run test:e2e:production
```

The browser suite starts its own synthetic API and Caddy on ports 8001/5175.
Set `CADDY_BIN` to a Caddy executable path if it is not on PATH. It verifies deep links,
JSON API errors, missing assets and the real plan/approval/session flow. This does not
verify image construction, Render persistence, a real Google account or provider calls.
